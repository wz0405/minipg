# minipg — 미니 PG 결제·정산 파이프라인

결제 승인부터 일정산 배치, 지급까지 — PG의 돈이 흐르는 길을 끝까지 구현한 프로젝트입니다.

라이브 데모: https://gks0405.synology.me:8090 (Synology NAS 상시 배포)

```
결제 (7수단) → 거래 원장 → 수수료 산정(원가/판가) → 일정산 배치 → 지급예정일 산출 → 지급
```

- 결제 데모 — 구매자 입장, "어떻게 결제할까요?"
- 가맹점센터 — 가맹점 입장, "언제 얼마 정산받나요?"
- 운영관리 — PG 내부 입장, 시딩·배치·마진

## 결제수단

| 수단 | 방식 | 핵심 |
|---|---|---|
| 카드 (결제창) | 나이스페이 인증결제 | 서버 서명 → 인증 → 승인. 상점키는 서버 밖으로 안 나감 |
| 카드 (수기) | 키인 — 카드번호·유효기간·생년월일·비밀번호 앞 2자리 | 카드정보 암호화 전송, 원본 비저장·마스킹만 보관 |
| 가상계좌 | 자체 채번 — 제휴사 벌크 계좌풀 | 풀에서 비관락으로 할당, 입금통보 웹훅으로 완결, 만료 시 회수 |
| 정기결제 | 빌키 발급 → 회차 승인 | 빌키만 보관, 카드 원본은 발급 즉시 폐기 |
| 휴대폰결제 | 다날 — 본인인증 → 승인 확정 | 통신사 소액결제, 인증 후 거래번호로 서버 승인, 요금 합산 |
| 머니/포인트 | 자체 원장 선불 (소진순서 복합결제) | 매체를 순서 고정 비관락으로 잠그고 순회 차감, 그룹 단위 취소 복원 |
| 오프라인 단말 | VAN 통보 수신 — 연결형 TCP 바이너리 전문 | 단말번호로 가맹점 역조회, 전문의 거래일시로 스탬핑, 재전송 멱등 |

## 설계에서 지킨 것들

거래 원장은 INSERT-only다. 취소는 갱신이 아니라 음수 금액의 별도 행으로 남긴다.
원장을 고치기 시작하면 "그 시점에 무슨 일이 있었나"를 영원히 답할 수 없게 된다.

PG 승인과 원장 적재는 한 몸이고, 깨지면 망취소한다. PG 승인은 떨어졌는데 내부 적재가
실패하면 고객 카드만 긁힌 유령거래가 남는다. 이 경우 즉시 제휴사 승인을 되돌린다.
승인 요청 전에 거래번호를 미리 확보해 두는 이유이기도 하다.

결과통보는 승인 응답을 붙잡지 않는다. 가맹점 서버통보·전표 발송류는 승인 트랜잭션 밖,
별도 스레드에서 처리한다. 통보 실패는 재통보로 복구할 영역이지 승인을 되돌릴 사유가 아니다.

잔액은 경합을 전제로 설계하되, 문제 모양에 맞춰 잠금을 고른다. 선불 결제는
소진순서(머니→포인트)로 여러 매체에 걸쳐 차감될 수 있어, 대상 매체를 순서를 고정해
비관락으로 잠근 뒤(교차 데드락 방지) 그 잠금 안에서 총잔액 검증과 순회 차감을 한
트랜잭션으로 끝낸다. 매체별 세부 거래는 같은 원거래번호로 묶어 취소를 그룹 단위로 되돌린다.
가상계좌 풀 할당도 비관락이지만 이유는 다르다 — 미사용 계좌 하나를 집어 그 계좌번호를
돌려받아야 하기 때문이다. 반대로 단일 행·평문 잔액이라면 조건부 갱신 한 번이 더 단순하다.
같은 정합성 요구라도 다중 행·순서 의존이면 잠금 후 판정이, 단건이면 조건부 갱신이 정답이다.

금액은 서버가 기억한 값만 믿는다. 주문 사전등록 금액과 승인 시도 금액을 대조해
클라이언트 변조를 승인 전에 차단한다.

배치는 멱등하다. 일정산은 같은 정산일 재실행 시 지우고 다시 만든다. 수수료는 승인 시점이
아니라 배치 시점에 계산하고 적용 요율을 스냅샷으로 남긴다 — 정책 변경 후 재정산이
가능해진다. 취소 수수료는 원거래 계산의 부호 반전이다(절사 비대칭 방지).

지급예정일은 영업일 기준이다. 거래일에 N영업일을 더하되 주말·공휴일은 이월하고,
지급 배치가 예정일 도래분을 지급완료로 전환한다.

## 아키텍처 — 프로세스 템플릿 + 제휴사 어댑터

레이어드(컨트롤러→서비스→DAO)가 아니라, 결제 시스템에서 검증된 형태로 짰다.
모든 전문이 같은 골격(before → do → after)을 타고, 제휴사와 업무는 빈 별명으로 찾아간다.

```
브라우저/가맹점 ── HTTP ──> 컨트롤러 (프로토콜 변환만)
                              │ loopback TCP — 개행 구분 JSON 전문
                              ▼
                        결제 게이트웨이 (Netty)
                          ├ 이벤트루프: 프레이밍·디코딩까지만
                          └ 비즈니스 executor(가상스레드)로 격리
                              │  전문 코드로 프로세스 빈 조회 → 곧 라우팅
                              ▼
                    프로세스 골격
                      ├ before : 검증 — 결제요청·금액·잔액·원거래 (조회까지만)
                      ├ do     : 제휴사 통신 — 트랜잭션 밖, 제휴사 코드로 어댑터 조회
                      ├ after  : 원장 반영 — 트랜잭션 안, 실패 시 프레임이 망취소로 뒷수습
                      └ postCommit : 커밋 후 — 가맹점 서버통보 (별도 스레드)
```

취소·채번·입금통보·빌키발급·선불도 전부 같은 골격이다. 취소는 원장에 남긴 제휴사 코드로
어댑터를 역룩업하므로, 어떤 제휴사 거래든 취소 코드는 하나다.

제휴사 확장 비용은 클래스 하나다. 승인·취소·망취소 계약을 구현해 제휴사 별명으로
등록하면 검증·원장·망취소·통보의 공통 흐름을 그대로 탄다. 실제로 나이스페이(구형 전문:
해시 서명, 카드정보 대칭키 암호화), 카카오페이(REST: 준비→리다이렉트→토큰 승인),
다날 휴대폰결제(본인인증 후 거래번호로 서버 승인)처럼 스펙이 전혀 다른 세 제휴사가
어댑터 안에서만 다르고 밖은 동일하다.

제휴사 통신을 트랜잭션 밖에 두는 이유는, 외부 API 지연이 DB 커넥션 점유로 전이되면
결제 전체가 밀리기 때문이다. 그 대가로 생기는 "승인 후 내부 실패" 구간의 뒷수습(망취소)을
프레임 레벨에서 보장한다.

수신 채널은 프로토콜만 다르고 업무는 하나다. 개행 구분 JSON(내부 루프백) 옆에
오프라인 단말망 통보(전문길이+헤더+바디의 연결형 TCP 바이너리)가 나란히 뜬다. TCP는
경계 없는 스트림이라 전문이 쪼개지거나 붙어 올 수 있고, 길이필드만큼 쌓일 때까지 기다렸다
정확히 한 전문씩 자르는 것이 프레이머의 몫이다. 각 게이트는 거기까지만 책임지고 같은
프로세스 골격으로 합류하므로, 수신 채널이 늘어도 업무 코드는 늘지 않는다.

| 모듈 | 역할 |
|---|---|
| common | 도메인·매퍼·수수료 산식·정산/시딩 (api/batch 공유) |
| api | 결제 게이트웨이(전문·프로세스·어댑터) + REST + 화면 서빙 |
| batch | 일정산 → 지급 / 자동취소 동기화 / 계좌풀 회수 (스케줄 잡) |
| infra | docker-compose(DB + api + batch), 스키마 |

화면은 호스티드 결제창이라 결제 서버가 정적 리소스로 직접 서빙한다(랜딩·결제·가맹점센터·운영관리).

## 정산 심화 — 알고 잘라낸 것들

이 데모의 정산은 거래 → 원가/판가 수수료 → 일정산 → 지급예정 → 지급완료까지다.
실무 풀스펙에는 그 뒤가 더 있고, 각각 어디에 붙는지는 설계돼 있다.

| 개념 | 무엇인가 | 붙는 자리 |
|---|---|---|
| 임의 지급보류/해제 | 사고·심사 사유로 특정 가맹점 지급을 멈췄다 푸는 것 | 정산 집계에 보류 상태·사유, 지급 배치가 보류 건 스킵 |
| 별도 가감 | 위약금·프로모션 등 정산금 외 수기 조정 | 가감 원장 신설, 지급액 합산 시 반영 |
| 상계 처리 | 환불채권 등 음수 정산을 다음 지급에서 차감 | 지급 배치에서 이월 잔액 관리 |
| 차액정산 (영중소) | 우대수수료 적용분을 사후 환급 | 매입 확정 데이터와 요율 차액 재계산 배치 |
| 서브몰 정산 | 하위몰 등록 후 정산을 분리 지급 | 가맹점 계층 + 정산 그레인에 서브몰 축 추가 |
| 세금계산서 | 수수료에 대한 역발행 | 월 마감 후 가맹점별 수수료 집계 → 발행 데이터 |
| 담당자 확정·송금 | 정산 확정 승인 후 은행 이체 실행 | 지급완료 전 확정 단계 + 이체 연동 |

## 정직한 범위 표기

- 배치 프레임워크: Spring Batch 대신 스케줄 잡으로 갔다. 이 규모(일 수천 건, 단일
  인스턴스)에서는 chunk·restart의 이점보다 운영 단순함이 크다고 판단했고, 멱등 재실행으로
  복구 시나리오를 대신한다. Spring Batch는 구조와 전환 지점(대량화 시 chunk 처리, 메타
  기반 재시작)을 이해하는 수준이다.
- 결제창 연동: 인증창 내부(카드사 인증 체인)는 PG가 제공하는 블랙박스로 두고, 서명·승인·
  망취소 등 가맹점/PG 서버 측 책임 구간을 구현했다.
- 제외한 것: 부분취소, 지급보류·별도가감, 대리점 다단계 정산, 카드정보 저장(비저장 정책으로
  회피). 각각 어디를 어떻게 확장하는지는 설계 문서에 적어 두었다.

## 실행

```bash
cd infra && docker compose up -d      # DB + api + batch
```

나이스페이 테스트키는 환경변수로만 주입한다(미설정 시 스텁 모드로 전체 파이프라인 동작).

나이스페이 테스트 환경은 매일 23시에 당일 거래를 전건 자동취소한다. 이를 숨기지 않고
파이프라인에 편입했다 — 심야 동기화 배치가 취소행을 적재하고, 다음날 일정산에서 승인·취소가
상쇄되는 "취소 반영 정산"이 매일 자동 시연된다.
