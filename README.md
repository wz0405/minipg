# minipg — 미니 PG 결제·정산 파이프라인

결제 승인부터 일정산 배치, 지급까지 — PG의 돈이 흐르는 길을 끝까지 구현한 프로젝트입니다.

**라이브 데모**: https://gks0405.synology.me:8090 (Synology NAS 상시 배포)

```
결제 (6수단) → 거래 원장 → 수수료 산정(원가/판가) → 일정산 배치 → 지급예정일 산출 → 지급
```

- **결제 데모**: `/checkout.html` — 구매자 입장, "어떻게 결제할까요?"
- **가맹점센터**: `/merchant.html` — 가맹점 입장, "언제 얼마 정산받나요?"
- **운영관리**: `/admin.html` — PG 내부 입장, 시딩·배치·마진

## 결제수단

| 수단 | 방식 | 핵심 구현 |
|---|---|---|
| 카드 (결제창) | 나이스페이 v3 인증결제 | 서버 서명 → 인증 → NextAppURL 승인. 상점키는 서버 밖으로 안 나감 |
| 카드 (수기) | 키인 — 카드번호/유효기간/생년월일/비번2 | 카드정보 AES 암호화 전송, **원본 비저장·마스킹만 보관** |
| 가상계좌 | **자체 채번** — 제휴사 벌크 계좌풀 | 풀에서 비관락(FOR UPDATE) 할당, 입금통보 웹훅으로 완결, 만료 시 회수 |
| 정기결제 | 빌키(BID) 발급 → 회차 승인 | 빌키만 보관, 카드 원본은 발급 즉시 폐기 |
| 머니/포인트 | **자체 원장** 선불 | 조건부 UPDATE로 잔액부족 원자 차단, 취소 시 원거래 기준 복원 |

## 설계에서 지킨 것들

**거래 원장은 INSERT-only.** 취소는 UPDATE가 아니라 음수 금액의 별도 행이다.
원장을 고치기 시작하면 "그 시점에 무슨 일이 있었나"를 영원히 답할 수 없게 된다.

**PG 승인과 원장 적재는 한 몸 — 깨지면 망취소.** PG 승인은 떨어졌는데 내부 적재가
실패하면 고객 카드만 긁힌 유령거래가 남는다. 이 경우 즉시 망취소(NET CANCEL)로
PG측 승인을 되돌린다. 승인 요청 전에 거래번호를 확보해 두는 이유이기도 하다.

**결과통보는 승인 응답을 붙잡지 않는다.** 가맹점 서버통보·전표 발송류는 승인
트랜잭션 밖, 별도 스레드(virtual thread)에서 처리한다. 통보 실패는 재통보로 복구할
영역이지 승인을 되돌릴 사유가 아니다.

**잔액류는 경합 전제로 설계한다.** 선불 잔액 차감은 `BLNC + Δ >= 0` 조건부
UPDATE(0행 = 잔액부족)로 원자적으로 끝내고, 가상계좌 풀 할당은 "어느 행이든 하나"를
잡아야 하므로 `SELECT ... FOR UPDATE` 비관락을 쓴다 — 같은 문제처럼 보여도
요구가 다르면 잠금 전략이 달라진다.

**금액은 서버가 기억한 값만 믿는다.** 주문 사전등록(결제요청) 금액과 승인 시도
금액을 대조해 클라이언트 변조를 차단한다 (`1004 금액 불일치`).

**배치는 멱등.** 일정산은 같은 정산일 재실행 시 DELETE 후 재생성. 수수료는 승인
시점이 아니라 배치 시점에 계산하고 적용요율을 스냅샷으로 남긴다 — 정책 변경 후
재정산이 가능해진다. 취소 수수료는 원거래 계산의 부호 반전(절사 비대칭 방지).

**지급예정일은 영업일.** 거래일 + N영업일, 주말·공휴일 이월. 지급 배치가
예정일 도래분을 지급완료로 전환한다.

## 아키텍처 — 프로세스 템플릿 + 제휴사 어댑터

레이어드(컨트롤러→서비스→DAO)가 아니라, 결제 시스템에서 검증된 형태로 짰다:
**모든 전문이 같은 골격(before → do → after)을 타고, 제휴사·업무는 빈 별명으로 찾는다.**

```
브라우저/가맹점 ── HTTP ──> 컨트롤러 (프로토콜 변환만)
                              │ loopback TCP — 개행 구분 JSON 전문
                              ▼
                        PayGate (Netty)
                          ├ 이벤트루프: 프레이밍·디코딩까지만
                          └ 비즈니스 executor(virtual thread)로 격리
                              │  getBean("process|" + cmd)   ← 전문 코드가 곧 라우팅
                              ▼
                    AbstractPayProcess (업무 골격)
                      ├ before : 검증 — 결제요청 대조·금액·잔액·원거래 (DB 조회까지만)
                      ├ do     : 제휴사 통신 — 트랜잭션 밖
                      │            getBean("partner|" + 제휴사코드).approve()
                      ├ after  : 원장 반영 — 트랜잭션 안 { TR_MSTR INSERT, 주문 상태 }
                      │            실패 시 프레임이 partner.netCancel()로 뒷수습
                      └ postCommit : 커밋 후 — 가맹점 서버통보 (별도 스레드)
```

**승인 한 건의 흐름 (카드 결제창 기준)**

```
[APPROVE 전문] ─▶ process|APPROVE
  before : 결제요청(reqId) 존재·중복승인·금액 대조 → 위반 시 1003/1005/1004
  do     : partner|NICEPAY .approve()  — 인증토큰으로 NextAppURL 승인 (성공 3001)
  after  : TX { 원장 승인행 INSERT · 주문 승인완료 }  — 여기서 깨지면 즉시 망취소
  postCommit : notifyUrl 서버통보 (virtual thread, 3회 재시도)
```

취소·채번·입금통보·빌키발급·선불도 전부 같은 골격이다. 취소는 원장에 남긴
PARTNER_CD로 어댑터를 역룩업하므로, 어떤 제휴사 거래든 취소 코드는 하나다.

**제휴사 확장 비용 = 클래스 하나.** `PartnerAdapter`(approve/cancel/netCancel)를
구현해 `partner|코드` 별명으로 등록하면 승인·취소·망취소·원장·통보의 공통 흐름을
그대로 탄다. 실제로 나이스페이(구 webapi 전문: SHA-256 서명, AES 카드암호화,
euc-kr 폼)와 카카오페이(REST: ready→redirect→pg_token 승인)처럼 스펙이 전혀 다른
두 제휴사가 어댑터 안에서만 다르고 밖은 동일하다.

제휴사 통신을 트랜잭션 밖에 두는 이유: 외부 API 지연이 DB 커넥션 점유로 전이되면
결제 전체가 밀린다. 그 대가로 생기는 "PG 승인 후 내부 실패" 구간의 뒷수습(망취소)을
프레임 레벨에서 보장한다.

| 모듈 | 역할 |
|---|---|
| `backend/common` | 도메인·매퍼·수수료 산식·정산/시딩 서비스 (api/batch 공유) |
| `backend/api` | 결제 게이트웨이(전문·프로세스·어댑터) + REST |
| `backend/api/src/main/resources/static` | 화면 전부 — 랜딩·결제·가맹점센터·운영관리 (호스티드 결제창이라 결제 서버가 직접 서빙) |
| `backend/batch` | @Scheduled: 04:00 일정산 → 06:00 지급 / 23:30 자동취소 동기화 / 00:10 계좌풀 회수 |
| `infra` | docker-compose (MariaDB + api + batch), 스키마 |

## 정산 심화 — 알고 잘라낸 것들

이 데모의 정산은 "거래 → 원가/판가 수수료 → 일정산 → 지급예정 → 지급완료"까지다.
실무 풀스펙에는 그 뒤가 더 있고, 각각 어디에 붙는지는 설계돼 있다:

| 개념 | 무엇인가 | 이 구조에 붙는 자리 |
|---|---|---|
| 임의 지급보류/해제 | 사고·심사 사유로 특정 가맹점 지급을 멈췄다 푸는 것 | SM_STMT에 보류 상태·사유 컬럼, 지급 배치가 보류 건 스킵 |
| 별도 가감 | 위약금·프로모션 등 정산금 외 수기 조정 | 가감 원장(INSERT-only) 신설, 지급액 합산 시 반영 |
| 상계 처리 | 환불채권 등 음수 정산을 다음 지급에서 차감 | 지급 배치에서 이월 잔액(캐리오버) 관리 |
| 차액정산 (영중소) | 우대수수료 적용분을 사후 환급 | 매입 확정 데이터와 요율 차액 재계산 배치 |
| 서브몰 정산 | 하위몰 등록 후 정산을 분리 지급 | 가맹점 계층 테이블 + 정산 그레인에 서브몰 축 추가 |
| 세금계산서 | 수수료에 대한 역발행 | 월 마감 후 가맹점별 수수료 집계 → 발행 데이터 생성 |
| 담당자 확정·송금 | 정산 확정 승인 후 은행 이체 실행 | 지급완료 전 확정 단계 삽입 + 이체 API/파일 연동 |

## 정직한 범위 표기

- **배치 프레임워크**: Spring Batch 대신 `@Scheduled`를 썼다. 이 규모(일 수천 건,
  단일 인스턴스)에서는 chunk/restart의 이점보다 운영 단순함이 크다고 판단했고,
  멱등 재실행(DELETE-INSERT)으로 복구 시나리오를 대신한다. Spring Batch는 구조와
  전환 지점(대량화 시 chunk 처리·메타테이블 기반 재시작)을 이해하는 수준이다.
- **결제창 연동**: 인증창 내부(카드사 인증 체인)는 PG가 제공하는 블랙박스로 두고,
  서명·승인·망취소 등 가맹점/PG 서버 측 책임 구간을 구현했다.
- **제외한 것**: 부분취소(잔액 체인), 지급보류/별도가감, 대리점 다단계 정산,
  PCI-DSS 수준 카드정보 저장(비저장 정책으로 회피). 각각 어디를 어떻게 확장해야
  하는지는 설계 문서에 적어 두었다.

## 실행

```bash
cd infra && docker compose up -d      # MariaDB + api(8080) + batch
```

나이스페이 테스트키는 환경변수로만 주입한다 (미설정 시 스텁 모드로 전체 파이프라인 동작):

```
NICEPAY_AUTH_MID / NICEPAY_AUTH_KEY     # 결제창
NICEPAY_KEYIN_MID / NICEPAY_KEYIN_KEY   # 수기·빌링
```

나이스페이 테스트 환경은 매일 23시에 당일 거래를 전건 자동취소한다.
이를 숨기지 않고 파이프라인에 편입했다: 23:30 동기화 배치가 취소행을 적재하고,
다음날 일정산에서 승인·취소가 상쇄되는 "취소 반영 정산"이 매일 자동 시연된다.
